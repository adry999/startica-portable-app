# Filiale (Faza 6) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two (or more) branches of the same kindergarten in one install, with **completely separate data** per branch (`docs/design/screens/17-filiale.md`): a branch selector under the logo (13a), an unsaved-form guard on switch (13b), a „Filiale” tab in Backup și setări (13c), the branch name in the topbar eyebrow and on the startup screen, and the „Ambele” option of the Raport contabil export (deferred from `20-raport-contabil.md` in `INTREBARI.md`).

**Architecture:** One SQLite file + one data/backup folder per branch; the server keeps exactly **one open branch at a time** („branch context” = today's `createApplication` body) and swaps it on `POST /api/branches/select`. A tiny JSON registry outside the branch folders (`filiale.json`) lists the branches and the last opened one. The existing install becomes branch #1 **in place** (no file moves). The webapp switches branch by a page reload at the same module path, so no hook or screen needs to become branch-aware.

**Tech Stack:** Node 22 vanilla ESM + `node:sqlite` + `node --test`; React 19 + Vite + TS + Vitest/RTL in `webapp/`. No new dependency.

**Spec:** `docs/design/screens/17-filiale.md` (authoritative), `18-sincronizare.md` (read for compatibility only — sync is **not** built here), `00-comun.md`, `docs/design/Filiale.dc.html#13a–13c`, `Sidebar.dc.html`; `docs/design/README.md` (Sidebar section: logo 46 px, version moves to the „Backup și setări” row).

## Decisions (read before coding)

1. **Storage: one SQLite file per branch, not `branchId` on every row.** Reasons: (a) the isolation criterion („nicio dată a unei filiale nu apare în cealaltă — există test”) is guaranteed by construction — a query cannot forget a `WHERE branch_id=?` that does not exist; (b) zero blast radius: every repository, route, service, `readSnapshot()`, `runRevisionTransaction`, `replaceAllRecords`, backup (`VACUUM INTO` of the whole file), restore, `sms_log`, `sms_templates`, `attendance`, `audit_changes`, `requests`, `settings` stay untouched; (c) backups/restore are per branch for free and a restore can never mix branches; (d) `meta.revision` stays per branch — the client's optimistic concurrency model is unchanged; (e) sync (18) maps 1:1: a branch dataset on the reconciliation server = one local file, „download branch X onto computer Y” = create `Filiale\<folder>` and pull, and the per-record `branchId` the sync spec asks for is implied by the file (it is added to the outbox rows, not to `records`). The spec itself leans this way („propriul folder de date/backup … sau sunt folosite baze separate”).
2. **Runtime switching = swap the branch context behind the HTTP server.** Today `createApplication` opens one DB and builds every repository/route as closures over it. That body becomes `createBranchContext(branch)` (returns `{ branch, db, dbFile, backups, dispatchRequest, runStartupSweeps, close }`), and `createApplication` keeps a mutable `active` context; `createServer((req,res) => active.dispatchRequest(...))`. Switching = backup the old branch (`schimbare-filiala`), open the new context, point `active` at it, close the old DB, run the startup sweeps on the new one. No route signature changes. Rejected: one application instance per branch (N open DBs, N backup timers, a routing layer every route would have to learn) and a reopen-in-place of the same `db` variable (repositories capture `db` by value, so the handle cannot be swapped underneath them).
3. **Branch registry: `filiale.json` in the install home, not inside any branch and not in SQLite.** `{ version: 1, lastBranchId, branches: [{ id, name, color, address, createdAt, folder }] }`, written atomically with `#core/server/files/json-file.mjs`. `id` is a UUID (must be globally unique for sync); `folder` is `null` for the migrated branch (legacy layout: `<home>\Startica_Date`, `<home>\Startica_Backup`) or a relative folder under `<home>\Filiale\` for branches created in the app. JSON, not a global DB: it is 5 fields, the C# launcher can read it without a SQLite driver (Telegram task, future „open branch X”), and it follows the `notify-schedule.json` / `telegram.json` precedent.
4. **Migration of the existing install = branch #1 stays where it is.** On first start without `filiale.json`: open the legacy layout exactly as today (backup `pornire` runs as always), then write the registry with one branch `{ id: randomUUID(), name: kindergarten.name || 'Filiala principală', color: 'orange', address: kindergarten.address, folder: null }`. No file is moved or copied, so nothing can go wrong with a real user's data; idempotent because the registry's existence is the marker. A registry that exists but does not parse **stops startup with a clear message** — never silently recreated (that would orphan branch #2's folder).
5. **New branch folder: `<home>\Filiale\<slug>\{Startica_Date,Startica_Backup}`** (slug from the name at creation, `-2` suffix on collision; renaming does not move the folder). Logs (`Jurnale\`) and `startica.port` stay per install. The branch DB is created eagerly on „+ Adaugă filială” (schema applied, then closed) so counts and the folder exist immediately.
6. **Per branch (automatically, because they live in the branch DB or data folder):** records, `attendance`, `sms_log`, `sms_templates`, `audit_changes`, all `settings` keys (`kindergarten`, `planPresets`, `notificationPreferences`, `exchangeRates`/`exchangeRateSources`, `externalDir`, `receipt*`), `sms.json`, `telegram.json`, `telegram-stare.json`, backups and their retention. **Per install:** session token, version, port file, logs, the registry, the Telegram scheduled task and its time mirror `notify-schedule.json`.
7. **BNM rate rule without a shared store.** Each branch keeps its own `exchangeRates`; the backfill `refreshExchangeRateIfMissing` runs on **every context open** (process start and switch), not only at process start, so both branches fetch the same published BNM value for each day. A manual correction (`sources[date]='manual'`) lives only in the branch where it was made — exactly the spec. No cross-branch copy.
8. **Telegram digest runs for every branch that has `telegram.json`.** `runTelegramDigest({ home })` iterates the registry and runs the existing per-branch logic on each branch's `dataDir` (its own `telegram-stare.json`); exit code = worst of the runs. `notify-schedule.json` (read by the launcher from `<home>\Startica_Date`) is written to that **fixed install path** regardless of the active branch — the last branch to save its `digestTime` sets the task time; both branches are sent at that time.
9. **Webapp switch = `location.replace(<same module path>)` after the server confirmed the switch.** Every data hook in `webapp/` is fetch-once (`useEffect(..., [])`: `useExchangeRates`, `usePlanPresets`, `useKindergarten`, `useBackup`, `useAttendance`, SMS hooks…) and the session store is a module singleton. In-place switching would require a „branch epoch” in every one of them and any miss would leak branch A's data into branch B's screen. A reload at the same path keeps the module (criterion 3), resets filters and closes drawers (both are `useState`/nested routes), and makes the isolation guarantee hold in the browser too. The fade + „Se deschide <filiala>…” overlay is shown until the page unloads; the toast is shown after reload from a `sessionStorage` note.
10. **13b unsaved-form guard: a tiny module-level registry of dirty forms** (`webapp/src/shared/state/dirty-forms.ts`) that each form drawer feeds with `{ label, save }` while its values differ from the initial ones. Nothing like this exists today (`Drawer.shouldBlockClose` is unused). „Salvează și schimbă” calls the registered `save()`; if it fails or validation refuses, the user stays.
11. **Raport contabil „Ambele”: a read-only snapshot route, `GET /api/branches/records?id=`**, that opens the other branch's DB with `openDatabaseReadOnly`, returns `readSnapshot()` and closes — the only cross-branch read in the app, explicit and read-only. The Excel gets one `Încasări`/`Cheltuieli` pair per branch plus a common `Rezumat`. PDF (print) stays current-branch only.
12. **Not built:** deleting a branch (spec: nu se poate șterge), moving branch #1 into `Filiale\`, sharing an external backup folder between branches (the `/api/settings` guard refuses any branch's data/backup dir; the hint says one subfolder per branch), sync columns/outbox, „Lucrez fără legătură”, prima pornire (22).

## Spec ambiguities resolved here

- **A single branch (every existing install after migration):** the selector is still rendered (spec: „pe toate ecranele”), the dropdown lists one row with ✓ and „Administrează filialele →”; the eyebrow shows „… · FILIALA <NUME>” only when `branches.length > 1` (a lone install should not read „Filiala principală” on every screen).
- **„N copii · adresă” / „N copii · N grupe · salvat azi, ora”** for branches that are not open: counted by a read-only open of that branch's DB in `GET /api/branches` (`SELECT kind, COUNT(*) FROM records WHERE kind IN ('children','groups') GROUP BY kind`, archived included; `lastLocal` from its `settings`). A brand-new branch shows 0 · 0.
- **Colours:** `BRANCH_COLORS = ['orange','mint','yellow','pink']` = the four `PillTone`s; the selector border/square use `--<tone>` and `--<tone>-ink` tokens. Initials = first two letters of the name („Bu”, „Bo”), first upper-cased.
- **Switch while a mutation is pending / busy:** refused client-side with the existing message („Verifică operațiunea anterioară cu „Reîncarcă””); server-side a second concurrent select gets 409.
- **Filters reset** = whatever is `useState` (search text, pills, month). Persisted view modes (`view.*`, `*.viewMode` in `localStorage`) are per computer, not per branch, and are kept — they are layout, not data.
- **Startup screen line „filiala și versiunea” (21a):** shown once `/api/session` has answered (`session.state.branch`), i.e. from step 2 on.

## Global constraints

- `src/features/*` untouched except `report` (nothing there needs branch awareness). Branch code is composition/infrastructure: `src/core/server/branches/` (registry file, folder layout, read-only counts) and `src/app/server/` (context, routes). Shared pure rules in `#shared/domain/branch.mjs`.
- Only `@shared/ui` + `tokens.css` in `webapp/`; no new hex.
- Server errors via `fail(message, status)`; a local `catch` only to translate a corrupt-branch open into an operator message.
- Tests: `npm test` at root, `cd webapp && npm run typecheck && npm test`; `npm run check` at the end of each phase; `npm run test:e2e` once after Phase 2 (the launcher/Telegram task is touched indirectly).
- Conventional Commits, scopes `config`, `core`, `app`, `docs`, `report`, `backup`. No AI trailers.

### Task 2: `createBranchContext` + swappable `createApplication`

**Files:** create `src/app/server/create-branch-context.mjs`; modify `src/app/server/create-application.mjs`, `src/app/server/main.mjs`, `tests/support/start-test-application.mjs` (pass `home: dir`).

**`createBranchContext({ branch, dataDir, backupDir, home, logFile, root, version, sessionToken, autoBackupIntervalMs, allowShutdown, fetch, shutdown, branchRoutes })`** = the current body of `createApplication` from `openDatabase` to `createRouteDispatcher`, plus `branchRoutes` (Task 3) appended to `routes`. Returns:

```js
{ branch, db, dbFile, dataDir, backupDir, backups, recordRepository, readSetting,
  dispatchRequest, runStartupSweeps, close }
```

`runStartupSweeps()` = the four `try/catch` calls now in `main.mjs`'s `setTimeout` (expireHealthNotes, expireSmsLog, refreshExchangeRateIfMissing) — the `backup('pornire')` stays in `main.mjs` for process start; the switch does its own `schimbare-filiala` backup on the branch being closed. `close()` = `cancelScheduledBackup()` + `db.close()` (idempotent, keeps the `databaseClosed` guard).

**`createApplication(options)`** now:

1. resolves `home` (`options.home ?? options.root ?? ROOT`) and legacy dirs (`options.dataDir/backupDir` or `dataLayout(home)`) — **all existing tests keep passing unchanged**;
2. opens branch #1 first when the registry is missing: `context = createBranchContext(legacy)`, then `registry.ensure({ name: kindergarten.name || 'Filiala principală', address: kindergarten.address, color: 'orange', folder: null })` using `context.readSetting('kindergarten')`; when the registry exists, opens `registry.find(lastBranchId)` (falls back to the first branch if the id is unknown);
3. `let active = context; const server = createServer((req, res) => active.dispatchRequest(req, res, port))`;
4. `selectBranch(id)` (used by the route in Task 3):

```
if (id === active.branch.id) return active.branch
if (switching) fail('Schimbarea filialei e deja în curs.', 409)
const target = registry.find(id) ?? fail('Filială inexistentă.', 404)
switching = true
try {
  active.backups.cancelScheduledBackup(); active.backups.safeBackup('schimbare-filiala')
  let next; try { next = createBranchContext(target…) } catch (e) { console.error(e.stack); fail(`Filiala „${target.name}” nu s-a putut deschide: ${e.message}`, 500) }
  const previous = active; active = next; registry.setLastBranchId(id)
  setTimeout(() => { previous.close(); next.runStartupSweeps() }, 0)   // after the response left
  return next.branch
} finally { switching = false }
```

5. the returned object delegates to `active`: `get db()`, `get database()`, `backup`, `safeBackup`, `health`, `expireHealthNotes`, `expireSmsLog`, `refreshExchangeRateIfMissing`, `envelope`, plus `activeBranch()`, `selectBranch`, `registry`; `close()` closes `active`.

`main.mjs`: replace the four sweep calls with `app.runStartupSweeps()` (keep `app.backup('pornire')` before it); write `database: app.database` in the port file as today (informational only).

Tests (`create-application.integration.test.mjs`, add): `'prima pornire creează filiale.json cu filiala principală pe folderele vechi și nu mută nimic'` (seed a DB via `POST /api/import`, restart the app on the same dirs, assert the same `revision`, the registry file, `folder === null`), `'un registru corupt oprește pornirea cu mesaj'`.

## Compatibility notes for 18 — sincronizare (not built here)

- Branch `id` is a UUID from day one; the migrated branch gets one at registry creation, so „datele existente ale fiecărei filiale se urcă o singură dată” has a stable key.
- Per-record `branchId`/`revision`/`updatedAt`/`updatedByDevice` and the outbox will be **tables inside each branch DB** (the file already is the branch), so `records` and every repository remain as they are; the device token and server URL go next to `filiale.json` (per install), and „connect a computer with a 6-digit code” = write `filiale.json` + pull each branch into `Filiale\<folder>`.
- The switch route is the only place that opens/closes a branch; the sync worker will attach to the active context (`app.activeBranch()`) and get a `branch.changed` hook there — nothing in this plan blocks it.
